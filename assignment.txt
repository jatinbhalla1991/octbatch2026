# Ansible Assignment: Role-Based and Condition-Based Automation

## Objective
Develop an Ansible automation project using reusable roles and conditional logic to install and configure Nginx, manage users, and control services based on user-provided inputs.

### Task 1: Create an Ansible Role
1. Create an Ansible role named `nginx`.
2. Use `ansible-galaxy` to generate the role directory structure.
3. Install Nginx on Ubuntu or RHEL-based Linux systems.
4. Start and enable the Nginx service.
5. Deploy a custom `index.html` page using a template.
6. Use a handler to restart Nginx whenever its configuration changes.

### Task 2: Implement Condition-Based Automation
Create a playbook that accepts the following inputs:

- `web_server`: `nginx` or `docker`
- `environment`: `dev`, `test`, or `prod`
- `create_user`: `true` or `false`
- `service_action`: `start`, `stop`, or `restart`

Requirements:

1. Execute the Nginx role only when `web_server=nginx`.
2. If `web_server=docker`, install Docker and ensure its service is running.
3. Deploy an environment-specific web page based on the `environment` variable.
4. Create a Linux user named `devuser` only when `create_user=true`.
5. Start, stop, or restart the selected service according to `service_action`.
6. Display an error and stop execution if an invalid input is supplied.
7. Use `when`, `register`, `assert`, and `handlers` wherever appropriate.

### Task 3: Execution and Validation
1. Run the playbook with different combinations of input variables.
2. Verify that the correct role and conditional tasks execute.
3. Run a syntax check before execution.
4. Execute the playbook a second time and verify idempotency.
5. Document the results and explain how the conditions control task execution.

## Expected Commands

Create the role:

`ansible-galaxy role init nginx`

Check playbook syntax:

`ansible-playbook site.yml --syntax-check`

Run for development:

`ansible-playbook -i inventory site.yml -e "web_server=nginx environment=dev create_user=true service_action=start"`

Run for production:

`ansible-playbook -i inventory site.yml -e "web_server=docker environment=prod create_user=false service_action=start"`

## Submission Deliverables
- Ansible project directory structure.
- Role files, templates, handlers, and playbook.
- Inventory file.
- Execution outputs for both scenarios.
- Syntax-check output.
- Explanation of the conditional logic and idempotency results.

# Kubernetes Advanced Assignment: Autoscaling, Node Management & Blue-Green Deployment

## Objective

Create a Kubernetes cluster and implement different scaling strategies at both Pod and Node levels. Configure manual and automatic scaling, perform node scale-up and scale-down without application downtime, and implement Blue-Green deployment.

### Task 1: Create a Kubernetes Cluster

1. Create a Kubernetes cluster using AKS or EKS.
2. Configure a minimum of 2 worker nodes.
3. Deploy a sample application (Nginx, Java, Python, or Node.js).
4. Expose the application using a Kubernetes Service.
5. Verify that the application is accessible.
6. Deploy multiple replicas and verify that workloads are distributed across worker nodes.

**Expected outcome:** A working Kubernetes cluster with a running application accessible through a Service.

### Task 2: Implement Pod Autoscaling (HPA and VPA)

Implement both Horizontal Pod Autoscaler (HPA) and Vertical Pod Autoscaler (VPA).

**Part A: HPA – Horizontal Pod Autoscaler**

1. Configure CPU and memory requests and limits for your application.
2. Install and configure Metrics Server.
3. Configure HPA based on CPU utilization (e.g., 50% or 60%).
4. Configure minimum and maximum replica counts.
5. Generate application load using a load-testing tool.
6. Observe how Kubernetes automatically increases the number of Pods.
7. Stop the load and observe how Kubernetes scales down the Pods.

**Part B: VPA – Vertical Pod Autoscaler**

1. Install and configure VPA.
2. Configure VPA for your application.
3. Test VPA in recommendation mode.
4. Check the CPU and memory recommendations.
5. Configure VPA in Auto or controlled update mode.
6. Observe how the resource requests are adjusted.
7. Understand what happens to existing Pods when VPA applies resource changes.

**Part C: Manual vs Automatic Scaling**

Perform both operations:

- Manually increase the replicas using `kubectl scale`.
- Manually decrease the replicas.
- Configure HPA and observe automatic scale-up and scale-down.
- Compare manual scaling with automatic scaling.

**Expected outcome:** Demonstrate how HPA and VPA work, explain the difference between horizontal and vertical scaling, and provide screenshots of scaling activities.

### Task 3: Kubernetes Node Scale-Up and Scale-Down Without Downtime

In this task, you must scale the worker nodes while ensuring that your application remains accessible throughout the process.

**Part A: Manual Node Scaling**

1. Start with 2 worker nodes.
2. Increase the worker node count to 3 or 4.
3. Verify that new nodes join the cluster.
4. Check how Kubernetes schedules existing and newly created Pods.
5. Scale down the worker nodes.
6. Safely drain the node before removing it.
7. Verify that the application continues running during the operation.

**Part B: Automatic Node Scaling**

1. Configure Cluster Autoscaler.
2. Define minimum and maximum node counts.
3. Deploy an application with sufficient CPU and memory requests.
4. Generate additional workloads that cannot fit on the existing nodes.
5. Verify that Cluster Autoscaler automatically adds worker nodes.
6. Reduce the workload and observe node scale-down.
7. Verify that workloads are safely rescheduled before nodes are removed.

**Part C: Zero-Downtime Requirement**

Ensure that application downtime does not occur during node scale-up or scale-down.

Implement the following:

- Configure at least 3 application replicas.
- Configure Pod Disruption Budget (PDB).
- Configure readiness and liveness probes.
- Use node draining before node removal.
- Implement rolling updates where required.
- Verify application availability throughout the process.

**Expected outcome:** Demonstrate manual and automatic node scaling, safe node draining, workload rescheduling, and application availability during infrastructure changes.

### Task 4: Implement Blue-Green Deployment

Implement Blue-Green deployment for your application.

**Scenario:**

Your company currently runs Application Version 1 (Blue). A new version, Version 2 (Green), needs to be deployed without interrupting existing users.

**Implementation steps:**

1. Deploy Application V1 and name it Blue.
2. Expose Blue using a Kubernetes Service.
3. Verify that users can access Version 1.
4. Deploy Application V2 separately and name it Green.
5. Create separate Kubernetes Deployments and labels for both versions.
6. Test Green independently before switching traffic.
7. Change the Kubernetes Service selector from Blue to Green.
8. Verify that incoming traffic now reaches Version 2.
9. Monitor the new version for errors and application health.
10. If Version 2 fails, implement rollback by switching traffic back to Blue.
11. Verify that rollback works without requiring a complete redeployment.

**Additional challenge:**

- Implement Blue-Green deployment using Kubernetes manifests.
- Maintain separate replica counts for both versions.
- Verify traffic routing before and after the switch.
- Demonstrate rollback using a single Service selector change.

**Expected outcome:** Successfully switch application traffic from Version 1 to Version 2 and demonstrate rollback without application downtime.

## Submission Requirements

Submit the following:

1. Kubernetes cluster architecture diagram.
2. YAML files for Deployments, Services, HPA, VPA, PDB, and probes.
3. Screenshots of manual and automatic Pod scaling.
4. Screenshots of VPA recommendations and resource updates.
5. Screenshots showing node scale-up and scale-down.
6. Evidence of successful node draining and workload rescheduling.
7. Blue-Green deployment manifests.
8. Screenshots showing traffic switching and rollback.
9. A short document explaining the challenges faced and how they were resolved.

## Important Conditions

- Do not perform only theoretical implementation.
- All scaling operations must be demonstrated practically.
- Application availability must be verified during node maintenance.
- Do not delete a worker node directly without safely draining it.
- Demonstrate both scale-up and scale-down.
- Demonstrate successful rollback in Blue-Green deployment.

**Final Goal:** Build a Kubernetes environment that can handle changing workloads, automatically scale infrastructure, maintain application availability, and support safe application releases.

You are working as a DevOps Engineer in a fintech organization developing a Java-based payment application.

   - New code coverage should be at least 80%.

   - No new security vulnerabilities.
   - No new security hotspots left unreviewed.
6. Configure Quality Profiles for Java.
7. Configure branch analysis for main and feature branches.
8. Configure Pull Request analysis.
